## 0. 本書の使い方

### 0.1 本書は何か

本書は**仕様書ではない**。
本書は、このプロジェクトにおける**「何を作るか」ではなく「何をもって正しいと判断するか」**を定義する。

仕様書・UI設計・シナリオ・実装・アート・演出・サウンド・マーケティング資料のすべては、本書を根拠に是非を判断される。

### 0.2 本書は何ではないか

- 機能一覧ではない
- ロードマップではない
- 技術選定書ではない
- 「やりたいことリスト」ではない

### 0.3 効力の順位

```
1. プロジェクト憲章（本書）        ← 最優先。矛盾する下位文書は無効
2. 各領域のデザイン指針            （ゲーム / UX / アート / シナリオ / 技術）
3. 機能仕様書
4. 実装タスク・チケット
```

**下位文書が本書と矛盾した場合、下位文書を修正する。本書は修正しない。**
本書を修正する必要が生じた場合は、§1.3 の改訂プロセスに従う。

### 0.4 判断に迷ったときの最短手順

1. §5「ゲームデザイン10原則」に照らす
2. §13「機能適合チェックリスト」を通す
3. それでも決まらない場合 → §1.2「不可侵条項」に反しない範囲で、**より地味な方**を選ぶ

> このプロジェクトにおいて、迷ったときの正解はほぼ常に「派手な方」ではない。

## 1. プロジェクト憲章（Project Constitution）

### 1.1 憲章前文

私たちは、猫を「かわいい素材」として消費するゲームを作らない。
私たちは、猫を「育成対象」として最適化させるゲームを作らない。
私たちは、猫を「理解の対象」として提示する。

このゲームの主人公はプレイヤーである。
このゲームで変化するのはプレイヤーである。
猫は変化させられる対象ではなく、**理解されるべき他者**である。

私たちが提供するのは達成感ではない。
**「わかった」という静かな手触り**である。

### 1.2 不可侵条項（Immutable Clauses）

以下は、いかなる理由（売上・話題性・開発コスト・工期・外部要望）によっても変更・例外化してはならない。

| # | 条項 | 意味 |
|---|---|---|
| I-1 | 猫の内部状態を数値としてプレイヤーに表示しない | 好感度バー・懐き度%・ステータス画面の類は永久禁止 |
| I-2 | 猫をプレイヤーの命令で動かせない | 呼ぶ・誘う・環境で促すことはできるが、猫が従う保証は一切与えない |
| I-3 | レベル・経験値・能力値成長を導入しない | 成長するのはプレイヤーの理解であり、猫の性能ではない |
| I-4 | 勝敗・スコアランキング・ゲームオーバーを導入しない | 命に優劣をつける構造を作らない |
| I-5 | ガチャ・確率課金・スタミナ課金を導入しない | 命を確率で引く体験は本作の理念と両立しない |
| I-6 | 猫に対する暴力・虐待・体罰を選択肢として実装しない | 「やってみて失敗から学ぶ」対象にしてよい行為ではない |
| I-7 | 学習内容を、報酬（アイテム・実績）で釣って読ませない | 知識は報酬の対価ではなく、体験の副産物として届ける |
| I-8 | 実在の団体・業種・個人を敵役として描かない | 偏見をなくす作品が、別の偏見を生んではならない |
| I-9 | 「見送り」エンディングを失敗として演出しない | 迎えないという判断も、猫のための正しい判断でありうる |
| I-10 | プレイヤーを叱責・断罪するテキストを書かない | 罪悪感の操作によって価値観を変えさせない |

### 1.3 改訂プロセス

本書は生きた文書であるが、軽々に変えない。

- **§1.2 不可侵条項**: 改訂不可。改訂が必要なら、それは別のゲームである。
- **§2〜§5（理念・哲学・原則）**: プロジェクト責任者の承認 + 変更理由の文書化が必須。変更履歴を本書末尾に残す。
- **§6〜§14（設計指針・基準）**: 実プレイ検証で反証された場合に限り更新可。「作りやすいから」は改訂理由にならない。

改訂時は必ず以下を記録する。

```
- 改訂日 / 改訂者
- 変更前 → 変更後
- 変更理由（どの検証・どの事実に基づくか）
- 影響を受ける下位文書のリスト
```

## 2. プロジェクト理念

### 2.1 Purpose（目的）

> **プレイヤーが猫を理解すること。**

育てることではない。懐かせることではない。クリアさせることでもない。
ゲームを終えたとき、プレイヤーの中に**「猫はこう考えているのかもしれない」という視点**が残っていること。

### 2.2 Mission（使命）

1. 保護猫を迎えることへの**心理的ハードルを下げる**
2. 猫という動物への**理解を深める**
3. 保護猫への**偏見をなくす**
4. 正しい知識を押し付けず、**ゲーム体験として自然に学べる**ようにする

### 2.3 Vision（到達像）

プレイ後、プレイヤーがこう感じている状態。

- 「猫ってこう考えるんだ」
- 「保護猫を迎えてみたい」
- 「迎えるって、こういう責任なんだ」
- 「自分にもできるかもしれない」

### 2.4 理念が示す優先順位

競合したとき、上にあるものを優先する。

```
1. プレイヤーの理解が深まるか
2. 猫の描写が誠実か
3. 体験が心地よいか
4. 遊びとして面白いか
5. 実装しやすいか
```

> 「面白さ」は4位である。ただし4位であって不要ではない。
> 理解を運ぶ乗り物としての面白さは必須であり、理解を追い越す面白さは不要である。

## 3. コアコンセプト

### 3.1 一行定義

> **思い通りにならない同居人と、30日かけて言葉なしに分かり合っていく物語。**

### 3.2 三つの柱

| 柱 | 内容 | プレイヤーがすること |
|---|---|---|
| **観察** | 猫は言葉を持たない。行動・距離・時間・音・痕跡がすべての情報源 | 見る。記録する。気づく |
| **推理** | 見えた事象から、見えない理由を推し量る | 仮説を立てる |
| **環境改善** | 猫を変えるのではなく、猫が安心できる条件を整える | 部屋を、生活を、自分を変える |

### 3.3 コア体験ループ

```
観察する
  ↓
「なぜ？」が生まれる
  ↓
仮説を立てる
  ↓
環境や行動を変えてみる
  ↓
猫の反応を見る（期待通りとは限らない）
  ↓
仮説を更新する ＝ 理解が深まる
  ↓
観察する（前より深く見えるようになっている）
```

**このループは全編を通じて不変である。**
新機能はこのループを**深くする**ためにのみ追加してよい。ループを**置き換える**追加は却下する。

### 3.4 「答え合わせ」ではない、とは何か

| ❌ 答え合わせ型（採用しない） | ✅ 理解型（採用する） |
|---|---|
| 正解の行動を選ぶと◯が出る | 行動の結果として猫の様子が変わる |
| 「正解！ 猫は高い場所が好きです」 | 猫が棚の上に登り、そこから降りてこない |
| クイズに答えて知識を確認 | ノートに自分の言葉で仮説が記録される |
| 攻略情報を知っていれば早く進む | 攻略情報を知っていても、この個体には当てはまらないことがある |

### 3.5 30日という枠

- 30日は**トライアル期間**である。譲渡が確定していない状態を意味する。
- 1日は**不可逆**である。戻せない。この不可逆性が体験の重みを担保する。
- ただし30日は**カウントダウンではない**。「残り◯日」を焦燥として演出しない。
- 30日目に訪れるのは勝敗ではなく**決断**である。

## 4. デザイン哲学

### 4.1 猫は所有物ではない

猫はプレイヤーのリソースでもコンテンツでもない。
UI上でも、テキスト上でも、演出上でも、猫を「手に入れる」「攻略する」「解放する」といった語彙で扱わない。

### 4.2 コントロールではなく調整

プレイヤーが操作できるのは**環境と自分の振る舞い**だけである。
猫はそれに反応するが、従うわけではない。

```
プレイヤーが直接触れられるもの: 部屋・物・時間の使い方・自分の距離と動き
プレイヤーが直接触れられないもの: 猫の感情・猫の行動・猫の記憶
```

### 4.3 変わるのはプレイヤー

ゲーム開始時と終了時で、**猫の性格は本質的に変わっていない**。
変わっているのは、猫の振る舞いの意味を読み取れるようになったプレイヤーの側である。

> 猫が心を開いたのではない。プレイヤーが猫の言葉を読めるようになったのだ。

この一文は、演出・シナリオ・エンディングすべての設計根拠である。

### 4.4 数値は存在するが、見せない

内部シミュレーションには数値がある（再現性と一貫性のために必要）。
しかしそれは**プレイヤーには一切開示しない**。

プレイヤーが受け取ってよい情報は次の5系統のみ。

1. **行動**（どこにいる、何をしている）
2. **距離**（どこまで近づくか、どこで止まるか）
3. **時間**（どれくらい続くか、どれくらいで終わるか）
4. **音**（鳴き声・足音・喉の音）
5. **痕跡**（食器の減り、トイレ、抜け毛、爪とぎの跡、動いた物）

> UIに数値バーを出したくなったら、それは「行動で表現する方法を諦めた」サインである。設計に戻る。

### 4.5 失敗は情報であって罰ではない

失敗しても終わらない。しかし、なかったことにもならない。

- 猫が警戒を強める → 悪循環に入る → 抜け出すには時間と手間がかかる
- 抜け出す方法は必ず存在する（詰みは作らない）
- 失敗を「ミス」と表示しない。起きたことを、起きた通りに見せる

### 4.6 焦りは悪手である、と体験でわからせる

「焦るほど悪循環になる」は、テキストで警告するのではなく**メカニクスで実感させる**。

- 距離を詰めようとするほど、猫は距離を取る
- 何もしない日を過ごすと、猫の側から動きが出る
- **「今日は何もしない」が有効な選択肢として常に存在する**

### 4.7 知識より理解

| 知識 | 理解 |
|---|---|
| 猫は高い場所を好む | この子は、人の視線より上にいると安心できる |
| 猫は環境変化に弱い | 昨日トイレを動かしたから、今日食べていない |
| しっぽの動きは感情を表す | このしっぽの動き方は、こっちを気にしている合図だ |

本作が届けたいのは右列である。左列は右列に至る道具にすぎない。

## 5. ゲームデザイン10原則

すべての設計判断は、この10原則に照らして検証する。

---

### 原則1｜猫は命である

**意味**: 猫は消費されるコンテンツではなく、尊厳を持つ存在として扱われる。

**設計への影響**
- 猫を「リセット」「やり直し」「引き直し」できない
- 猫を捨てる・返す選択肢は存在するが、軽く扱わない
- 死・重篤な疾病は本編の脅しとして使わない（§9.4）

**違反例**: 「相性の悪い猫はリセマラで引き直せる」

---

### 原則2｜猫は個体差がある

**意味**: 「猫とはこういうもの」という一般論は、目の前の一匹には当てはまらないことがある。

**設計への影響**
- 個体は「性格プロファイル」を持ち、その内的論理は一貫している
- ただし**ランダムではない**。理不尽ではなく、**自明ではないだけ**
- 攻略情報の丸写しが常に通用しないこと自体が、メッセージである

**違反例**: 「猫は全員、マタタビで警戒が下がる」

---

### 原則3｜正解は一つではない

**意味**: 同じ状態に対する有効な打ち手は複数ある。最適解の一本道を作らない。

**設計への影響**
- 各課題に最低2通り以上の解決アプローチを用意する
- 「不正解ではないが、この子には合わない」という中間結果を許容する
- 攻略チャートが成立する構造を意図的に避ける

**違反例**: 「隠れている猫を出すには、必ず段ボールを置く」

---

### 原則4｜猫の気持ちは数値で見えない

**意味**: 不可侵条項 I-1 の実装原則。

**設計への影響**
- 好感度・信頼度・ストレス値のUI表示は禁止
- 「わかりやすさ」は数値ではなく**観察のしやすさ**で担保する
- プレイヤーの推測が外れる余地を常に残す

**違反例**: 「信頼度 62% / あと38%で撫でられます」

---

### 原則5｜猫は思い通りにならない

**意味**: 正しい行動をしても、望む結果が返らないことがある。

**設計への影響**
- 行動→結果の対応は確率的かつ文脈依存
- ただし**でたらめではない**。事後に「そうか、だからか」と説明がつく
- 「正しくやったのに報われない日」を意図的に設計に含める

**違反例**: 「正しい選択をすれば必ず猫が近づいてくる」

---

### 原則6｜焦るほど悪循環になる

**意味**: 前のめりな介入は事態を悪化させる。

**設計への影響**
- 過干渉に対して明確なネガティブフィードバックを設ける
- 悪循環は数日単位で持続し、即座には解けない
- ただし必ず出口がある。詰み状態を作らない
- **待つ・見る・何もしないが、常に選択可能である**

**違反例**: 「毎日たくさん行動したプレイヤーほど有利」

---

### 原則7｜観察が最大の攻略法

**意味**: 情報収集こそが本作の中心的な行為である。

**設計への影響**
- 観察行動にコストをかけさせない（気軽に何度でも見られる）
- 観察でしか得られない情報を必ず用意する
- 観察の解像度は、プレイヤーの理解の深まりに応じて**表現が変わる**
  （同じ仕草が、後半では違う意味に見える）

**違反例**: 「観察はスキップ可能なフレーバー」

---

### 原則8｜環境改善が最大の成長要素

**意味**: 本作における「成長」は、猫でもプレイヤーの数値でもなく、**空間と生活の質**である。

**設計への影響**
- 部屋・動線・高さ・隠れ場所・トイレ・食事・音・光・匂い・時間帯が設計対象
- 環境の変更は**猫のためのもの**であり、プレイヤーの装備ではない
- 「良い部屋」の正解は個体によって異なる

**違反例**: 「高級キャットタワーを買えば全個体の好感度が上がる」

---

### 原則9｜知識より理解を重視する

**意味**: 情報の量ではなく、腑に落ちた質を測る。

**設計への影響**
- 知識はテキストで先に与えず、現象を見せた後に言語化させる
- 用語より現象を先に置く（「転位行動」より「急に毛づくろいを始めた」）
- 監修済みの正確な知識を扱うが、**講義しない**（§7）

**違反例**: 「チュートリアルで猫の生態を10画面かけて説明」

---

### 原則10｜変わるのはプレイヤーである

**意味**: 本作の進行度とは、プレイヤー自身の視点の変化である。

**設計への影響**
- 進捗表現はプレイヤー側の資産（観察ノート、気づき、選択肢の増加）で示す
- 猫のパラメータ上昇として進捗を示さない
- エンディングはプレイヤーの理解の到達点を映す鏡である

**違反例**: 「30日目に猫のなつき度がMAXになってハッピーエンド」

## 6. プレイヤー体験設計

### 6.1 プレイヤーの立場

プレイヤーは飼い主候補である。まだ飼い主ではない。
この「まだ」が、30日間の緊張と誠実さの源である。

- **持っている権限**: 環境を変える、自分の行動を変える、時間の使い方を決める
- **持っていない権限**: 猫の感情、猫の行動、猫の過去

### 6.2 1日の構造

```
朝  ── 昨日の痕跡を確認する（食事・トイレ・移動の跡）
       ↓
日中 ── 観察する / 行動する（行動には時間コストがある）
       ↓
夜  ── 猫の様子を見る
       ↓
記録 ── 観察ノートに気づきを書き留める（プレイヤーの言葉で）
       ↓
翌日へ（不可逆）
```

**設計要件**
- 観察は無制限・低コスト（原則7）
- 介入行動は有限（1日にできることは限られる）
- **「何もしない」を明示的な選択肢としてUIに常設する**（原則6）

### 6.3 時間設計

| 項目 | 基準 |
|---|---|
| 全体プレイ時間 | 30〜60分 |
| 1日あたり | 1〜2分 |
| 中断可能性 | 1日単位で必ず中断・再開できる |
| 周回 | 可能。ただし2周目は「別の個体」であり「効率的な1周目」ではない |

> 30日 × 数分 = 短い。だからこそ1日の密度は「情報量」ではなく「印象の鮮明さ」で作る。

### 6.4 難易度の考え方

本作に難易度設定は置かない。
代わりに、**猫の個体差が自然な難易度差を生む**。

- 難しさ = 操作精度でも知識量でもなく、**観察の丁寧さ**
- 詰まる状態は「情報不足」であり、「操作ミス」ではない
- 詰まったプレイヤーへの救済は、答えの提示ではなく**観察の視点の提示**

### 6.5 プレイヤーの導線設計

| フェーズ | プレイヤーの状態 | 提供するもの |
|---|---|---|
| Day 1-5 | 何を見ればいいかわからない | 見るべき場所の存在を示す（答えは言わない） |
| Day 6-12 | 見方がわかってきた | 気づきが言語化される手応え |
| Day 13-20 | 試して、外して、悩む | 失敗が情報になる実感 |
| Day 21-27 | 読めるようになる | 同じ光景が違って見える演出 |
| Day 28-30 | 決断する | 判断材料。ただし答えは示さない |

### 6.6 エンディング設計原則

複数のエンディングを用意するが、**優劣をつけない**。

想定される着地（例）
- **正式譲渡** — この子と暮らしていける確信を得た
- **トライアル延長** — まだわからない。急がないという判断
- **見送り** — この環境ではこの子を幸せにできないという判断

いずれも「猫のために考え抜いた結果」として等しく肯定する。
**「見送り」を失敗として演出することは不可侵条項 I-9 違反である。**

エンディングの評価軸は結果ではなく、**プレイヤーがどれだけ猫を見ようとしたか**である。

## 7. 学習体験設計

### 7.1 学習の最小単位 —「気づき（Insight）」

本作における学習の単位は「知識項目」ではなく「気づき」である。

```
気づき = 観察した現象 + プレイヤーが立てた解釈 + それが確かめられた経験
```

三つが揃って初めて「気づき」として成立する。
どれか一つでも欠けたものは、ノートに記載しない。

### 7.2 提示順序（絶対厳守）

```
1. 現象を見せる          「猫が食器の前まで来て、食べずに戻った」
2. 疑問が生まれる        「なぜ？」
3. プレイヤーが仮説を持つ 「音がうるさい？ 場所が落ち着かない？」
4. 試す                  「食器を壁際に寄せてみる」
5. 結果を観る            「今日は食べた」／「今日も食べなかった」
6. 言語化される          ノートに気づきが残る
7. 一般化                「この子は、人の動線上では食べない」
```

**逆順は禁止である。**
先に「猫は落ち着かない場所では食べません」と教えてはならない。

### 7.3 知識UIの唯一性

知識を表示するUIは**観察ノート一つに限定する**。

- ノートはプレイヤーの行動によってのみ埋まる
- 未取得の項目を「？？？」でコレクション的に見せない（収集欲で埋めさせない = I-7）
- ノートの文体は**プレイヤーの一人称メモ**であり、教科書ではない

```
❌「猫は高所を好む習性がある。これは野生時代の…」
✅「棚の上にいるときは、こっちを見ても逃げない。目線より上だと平気なのかも」
```

### 7.4 情報の正確性と監修

- ノートに記載される内容は、猫の行動学・獣医療の観点で**事実として誤りがないこと**
- 断定できない事柄は断定しない（「〜と言われている」「個体差がある」）
- 監修者の確認を経ていない知識記述はリリースしない（§9.2）
- 現実の医療判断・飼育判断をゲーム内表現だけに依らせない旨を、適切な場所に明示する

### 7.5 押し付けないための禁則

| 禁則 | 理由 |
|---|---|
| チュートリアルでの生態講義 | 押し付けになる（Mission 4違反） |
| クイズ・正誤判定 | 「答え合わせ」構造になる（§3.4違反） |
| 実績・アイテムによる学習誘導 | 不可侵条項 I-7 違反 |
| ナレーターによる正解の断定 | プレイヤーの推理を奪う |
| プレイヤーの行動への説教 | 不可侵条項 I-10 違反 |

### 7.6 保護猫理解の扱い

Mission 3（偏見をなくす）に関わる要素は、特に慎重に扱う。

- 保護猫の過去は、**同情を引く装置として使わない**
- 「かわいそうだから迎える」ではなく「一緒に暮らせるから迎える」へ導く
- 他の入手経路や業種を貶めることで保護猫を持ち上げない（不可侵条項 I-8）
- 譲渡条件・トライアルの実務は、現実に即して正確に、かつ**過度に厳しくも甘くも描かない**

## 8. 感情体験設計

### 8.1 目指す感情のピーク

本作の最大の感情ピークは、次の瞬間である。

> **猫が近づいてきた瞬間ではなく、「なぜ近づいてきたのか」がわかった瞬間。**

演出予算・音楽・カメラワークのすべてを、この瞬間に最大配分する。

### 8.2 感情曲線（30日）

```
感情の質
  │
  │                                          ┌── 静かな確信
  │                          ／＼            ／
  │              ／＼      ／    ＼        ／
  │    ／＼    ／    ＼  ／        ＼    ／
  │  ／    ＼／        ＼            ＼／
  └──────────────────────────────────────────→ 日数
    1-5     6-12     13-20     21-27    28-30
   不安     発見     停滞と    読める   決断と
   無力     手応え   揺り戻し  実感     責任
```

| 期間 | 主感情 | 副感情 | 演出方針 |
|---|---|---|---|
| Day 1-5 | 不安・無力感 | 好奇心 | 猫は見えない。距離が遠い。静けさで満たす |
| Day 6-12 | 発見の喜び | 手応え | 小さな変化を、大げさにせず確実に伝える |
| Day 13-20 | 停滞・迷い | 悔しさ | 後退を起こす。ただし責めない |
| Day 21-27 | 安堵・信頼 | 愛着 | 同じ光景の見え方を変える。演出の再解釈 |
| Day 28-30 | 責任・決断 | 寂しさ | 選択を委ねる。感動を押し売りしない |

### 8.3 使ってよい感情、使ってはいけない感情

| ✅ 使ってよい | ❌ 使ってはいけない |
|---|---|
| 静かな喜び | 過剰な高揚 |
| 手応え | 達成感の演出（ファンファーレ等） |
| もどかしさ | 焦燥を煽る演出（残り日数の赤字点滅等） |
| 寂しさ | 罪悪感による行動誘導 |
| 愛着 | 依存を促す設計 |
| 責任の実感 | 断罪・説教 |

### 8.4 「かわいい」の扱い

猫のかわいさは本作の**手段でも報酬でもない**。理解の副産物である。

- かわいさで注意を引くビジュアル設計は行うが、**かわいさを進行の対価にしない**
- 「かわいい仕草」は必ず**行動学的な意味を持つ**（意味のない媚びる仕草を作らない）
- 誇張したアニメ的リアクション（目がハートになる等）は採用しない

### 8.5 沈黙と余白

本作において**何も起きない時間は、コンテンツである**。

- 猫が寝ているだけの時間を、退屈として排除しない
- BGMは常時鳴らさない。生活音と静寂を主体にする
- テキストで間を埋めない

## 9. ゲーム全体の品質基準

各項目は **［必達］／［目標］／［対象外］** で分類する。
［必達］を満たさない状態でリリース判断はできない。

### 9.1 体験品質

| 基準 | 区分 |
|---|---|
| コア体験ループ（§3.3）が全編を通して機能している | 必達 |
| 「何もしない」が有効な選択肢として成立している | 必達 |
| 同じ攻略手順で全個体をクリアできない | 必達 |
| 初見プレイヤーが説明書なしでDay 1を完了できる | 必達 |
| プレイ後に少なくとも1つ、自分の言葉で語れる気づきが残る | 必達 |
| 2周目で異なる発見がある | 目標 |

### 9.2 情報の正確性

| 基準 | 区分 |
|---|---|
| 猫の行動描写が行動学的に不自然でない | 必達 |
| 観察ノートの全記述が監修を通過している | 必達 |
| 断定できない事柄を断定していない | 必達 |
| 譲渡・トライアルの手続き描写が現実と乖離していない | 必達 |
| 医療・健康に関する免責表示がある | 必達 |

### 9.3 倫理・表現

| 基準 | 区分 |
|---|---|
| 猫への暴力・虐待表現が存在しない | 必達 |
| 特定の団体・業種・個人を敵役として描いていない | 必達 |
| プレイヤーを断罪するテキストが存在しない | 必達 |
| 「見送り」が失敗として演出されていない | 必達 |
| 同情を煽る過去設定に依存していない | 必達 |

### 9.4 センシティブ表現の扱い

- **死・重篤な疾病**: 本編の脅威・失敗条件として使用しない。触れる場合は情報として静かに扱い、演出で消費しない
- **多頭飼育崩壊・遺棄などの背景**: 直接描写せず、必要最小限の言及にとどめる
- **表現強度の事前告知**: センシティブな内容を含む場合、開始前に告知し、回避手段を用意する

### 9.5 UI / UX

| 基準 | 区分 |
|---|---|
| 猫の内部数値がUI上に一切存在しない | 必達 |
| 画面から「猫を見る」ことが常に可能 | 必達 |
| 情報の階層が3階層以内 | 必達 |
| スマホ縦持ち・片手操作で全操作が完結する | 必達 |
| 誤タップで不可逆な行動が発生しない | 必達 |
| UIが猫の観察を妨げない（画面占有率の上限を定める） | 必達 |

### 9.6 アート / 演出

| 基準 | 区分 |
|---|---|
| 猫の仕草がすべて実在する行動に基づいている | 必達 |
| 同じ仕草が状況によって異なる意味を持つよう演出されている | 必達 |
| 誇張されたアニメ的感情表現を使用していない | 必達 |
| 静止した画面が成立する（動きで間を埋めていない） | 目標 |
| 生活音・環境音が主体で、BGMが常時鳴っていない | 目標 |

### 9.7 技術

| 基準 | 区分 |
|---|---|
| PC / スマホの主要ブラウザで動作する | 必達 |
| 初回起動からDay 1開始まで、標準的なモバイル回線で短時間で到達する | 必達 |
| 通信断でもプレイ継続でき、進行が失われない | 必達 |
| セーブは自動。1日単位で確実に保存される | 必達 |
| インストール不要で遊べる | 必達 |
| ログイン必須にしない | 必達 |

> 数値目標（秒数・MB）は技術指針書で定義する。本書はその存在を義務づけるにとどめる。

### 9.8 アクセシビリティ

| 基準 | 区分 |
|---|---|
| 色のみで情報を伝えていない | 必達 |
| 音がなくても全情報が得られる（鳴き声は視覚的にも提示） | 必達 |
| 文字サイズ変更に対応 | 必達 |
| モーション低減設定に対応 | 目標 |
| 平易な日本語。専門用語には必ず現象での言い換えを併記 | 必達 |

### 9.9 対象外と明記するもの

- eスポーツ性・競技性
- ソーシャル機能（他プレイヤーとの比較・競争）
- 長期運営型のライブサービス設計
- 猫の外見カスタマイズによる収益化

## 10. 今後すべての設計書が従うべきルール

### 10.1 全設計書に必須の記載項目

いかなる仕様書も、冒頭に以下を含めなければならない。

```markdown
## この仕様が支える原則
- 原則◯: （どの原則を、どう具体化するか）

## コア体験ループへの位置づけ
- 観察 / 仮説 / 行動 / 反応 / 理解 のどこを担うか

## 不可侵条項との適合確認
- I-1 〜 I-10 のうち、抵触リスクがあるものと、その回避方法

## 判断が割れたときの基準
- この仕様の中で迷ったら、何を優先するか
```

これがない仕様書はレビューを受け付けない。

### 10.2 語彙の統制

プロジェクト全体で以下の語を使わない。

| 禁止語 | 代替 |
|---|---|
| 育成する | 一緒に暮らす / 環境を整える |
| 攻略する | 理解する |
| 好感度 / 懐き度 | （数値概念そのものを表に出さない） |
| クリア | 30日を終える / 決断する |
| 失敗 / ミス | うまくいかなかった / 反応が返らなかった |
| 正解 | この子に合っていた |
| 飼う（プレイヤー視点の所有表現として） | 迎える / 暮らす |
| ペット | 猫 / 家族 |

### 10.3 仕様の書き方

- **数値ではなく体験で書く**: 「警戒値を20下げる」ではなく「翌日、少し近い場所で寝るようになる」
- **プレイヤー視点で書く**: 「システムが判定する」ではなく「プレイヤーには◯◯に見える」
- **例外を明示する**: 「ただし、この個体では起きない」を必ず書く

### 10.4 レビューゲート

```
仕様ドラフト
   ↓
[Gate 1] 憲章適合レビュー（§13チェックリスト）  ← 落ちたら実装に進めない
   ↓
[Gate 2] 領域レビュー（ゲーム / UX / アート / 技術）
   ↓
[Gate 3] 監修レビュー（猫に関する事実を含む場合のみ）
   ↓
実装
   ↓
[Gate 4] 体験検証（§11.2 の観点で実プレイ確認）
```

Gate 1 は本書の遵守のみを見る。面白さや実装難度はここでは議論しない。

### 10.5 例外の扱い

本書に対する例外は**原則として認めない**。
どうしても必要な場合は、以下をすべて満たすこと。

1. §1.2 不可侵条項に抵触しないこと
2. 例外理由と有効期限を文書化すること
3. プロジェクト責任者が承認すること
4. 例外リストに登録し、定期的に解消を検討すること

「暫定的に」で始まった例外は必ず恒久化する。だから最初から認めない。

## 11. プロジェクト成功条件

### 11.1 成功の定義

> **プレイヤーの価値観が、プレイ前より少しだけ変わっていること。**

売上でも、DL数でも、話題性でもない。

### 11.2 評価指標

本作の指標は「猫が懐いたか」ではない。以下で測る。

#### 一次指標（体験の質）

| 指標 | 測るもの |
|---|---|
| 観察回数 | プレイヤーがどれだけ見ようとしたか |
| 仮説数 | どれだけ「なぜ」を考えたか |
| 環境改善の試行回数 | どれだけ猫に合わせようとしたか |
| うまくいかなかった後の再試行率 | 失敗から学べたか |
| 気づきの獲得数と、その言語化 | 理解が定着したか |

#### 二次指標（意識の変化）

プレイ後アンケート等で確認する。

- 「保護猫を迎えることへの心理的ハードルが下がったか」
- 「猫の行動の意味を、以前より想像できるようになったか」
- 「保護猫に対する印象が変わったか」
- 「猫を迎える責任について、具体的に考えられるようになったか」

#### 参考指標（体験の健全性）

- 30日完走率
- 中断からの復帰率
- 「何もしない日」の選択率（0%に近い場合、§4.6が機能していない）

### 11.3 失敗の定義

以下が観測されたら、それは設計の失敗である。

- プレイヤーが**攻略情報を見て最短で終わらせられる**
- プレイヤーが**猫を「攻略対象」として語る**
- プレイヤーが**「懐かせるゲーム」と説明する**
- プレイヤーが**プレイ後に何も語れない**
- プレイヤーが**罪悪感だけを残して終わる**
- 「見送り」を選んだプレイヤーが**自分を責めている**

### 11.4 やらないこと（成功のために）

- 数値目標のために体験を薄めない
- 話題化のために猫の描写を誇張しない
- 継続率のためにデイリー報酬を導入しない
- 収益のために不可侵条項を緩めない

## 12. 開発チーム全員が共有するべき価値観

職種を問わず、チーム全員が以下を自分の判断基準として持つ。

### V1. 私たちは猫の代弁者ではなく、観察者である

猫の気持ちを断定して書かない。私たちが描くのは**猫の振る舞い**であり、猫の内心ではない。

### V2. 「わかりやすくする」の前に「見えるようにする」を考える

情報が伝わらないとき、最初の選択肢はUIで数値を出すことではない。**猫の行動をもっとよく見せること**である。

### V3. プレイヤーを信頼する

説明しなくてもわかる。気づける。考えられる。
説明を足したくなったら、まず「なぜ気づけなかったか」を疑う。

### V4. 地味さを恐れない

このゲームは静かでいい。派手さは、このプロジェクトにおいてはリスクである。

### V5. 私たちは誰も責めない

プレイヤーも、猫を飼わない人も、猫を飼えなかった人も責めない。
このゲームは、誰かを正すためではなく、誰かの視野を広げるために作る。

### V6. 現実に責任を持つ

このゲームを遊んだ人が、現実で猫を迎えるかもしれない。
私たちが書いた一行が、現実の猫の暮らしに影響しうる。
**正確さは、演出よりも重い。**

### V7. わからないことは、わからないと書く

猫についてまだ解明されていないことは多い。断定は誠実さを損なう。

### V8. 迷ったら憲章に戻る

「面白そうだから」は理由にならない。
「原則◯に沿っているから」が理由になる。

| 猫を呼ぶと来てくれるコマンド | 却下 | I-2 / 原則5 |
| ミニゲームで遊んであげると仲良くなる | 却下 | 原則8（環境ではなく操作で解決している） |
| 猫の生態を学べる図鑑を実績解放式で | 却下 | I-7 / §7.3 |
| 猫の過去を描く回想シーン | 条件付き | 同情を煽らず、行動の理由を理解する材料になるなら可 |

| 部屋のレイアウト編集 | 採用検討 | 原則8の中核。ただし「正解の配置」を作らないこと |

## 14. 将来的に仕様が増えてもブレないための設計指針

### 14.1 レイヤー構造

機能は必ず以下のいずれかのレイヤーに属する。レイヤーをまたぐ機能は分割する。

```
┌─────────────────────────────────────┐
│ L0: 憲章レイヤー（本書）              │ 変更しない
├─────────────────────────────────────┤
│ L1: コアループ                        │ 変更しない
│     観察 / 仮説 / 行動 / 反応 / 理解   │
├─────────────────────────────────────┤
│ L2: 猫シミュレーション                │ 拡張のみ。表出方法は変えない
│     性格プロファイル / 行動決定        │
├─────────────────────────────────────┤
│ L3: 環境システム                      │ 拡張可
│     部屋 / 物 / 動線 / 生活リズム      │
├─────────────────────────────────────┤
│ L4: 表現レイヤー                      │ 自由に拡張可
│     演出 / アート / 音 / テキスト      │
└─────────────────────────────────────┘
```

**拡張は下から行う。** L4 → L3 → L2 の順で検討し、L1 に手を入れる必要が出たら設計が間違っている。

### 14.2 追加の作法

| やること | やらないこと |
|---|---|
| 既存の要素の**意味を増やす** | 新しい要素を**種類として増やす** |
| 観察できる対象を増やす | 操作できるコマンドを増やす |
| 個体差のバリエーションを増やす | 猫の能力の幅を増やす |
| 環境の相互作用を増やす | 環境アイテムの数を増やす |

> 「増やす」より「深める」。物が10個ある部屋より、意味が10通りある1つの物。

### 14.3 スケールの上限を先に決める

長期プロジェクトが壊れるのは、上限を決めなかったときである。

| 対象 | 上限の考え方 |
|---|---|
| 猫の個体数 | 増やしてよいが、**1周のプレイ時間は変えない** |
| 環境アイテム | 増やす前に、既存アイテムの意味を増やせないか検討する |
| 気づき（ノート項目） | 増やしてよいが、**1周で全部埋まらない**ことを前提にする |
| 日数 | 30日は変更しない。トライアル期間という現実の枠に対応するため |
| UI階層 | 3階層を超えない |

### 14.4 変更が起きたときの判定順序

```
1. その変更は L1（コアループ）を変えるか？
   → YES: 却下。別プロジェクトとして検討する
   → NO : 2へ

2. §1.2 不可侵条項に抵触するか？
   → YES: 却下
   → NO : 3へ

3. §13 チェックリストを通過するか？
   → NO : 差し戻し
   → YES: 4へ

4. §14.2「深める」側の変更か？
   → NO : 「増やす」変更として、なぜ必要かを追加で説明する
   → YES: 採用検討
```

### 14.5 意思決定の記録

すべての重要判断は、以下の形式で残す。

```markdown
### 決定: 〈タイトル〉
- 日付 / 決定者
- 背景（なぜ判断が必要になったか）
- 選択肢（検討した案）
- 決定内容
- 根拠となる憲章の条項
- 却下した案と、その理由
```

**「なぜやらなかったか」の記録は、「なぜやったか」より重要である。**
半年後に同じ提案が出たとき、この記録がプロジェクトを守る。

### 14.6 定期的な憲章監査

節目ごとに、以下を確認する。

```
□ 現在の仕様は §5 の10原則すべてを満たしているか
□ 不可侵条項に、なし崩し的な例外が生まれていないか
□ 語彙統制（§10.2）が守られているか
□ 「観察」より「操作」が増えていないか
□ 「何もしない」が選択肢として生きているか
□ 遊んだ人が「懐かせるゲーム」と説明していないか
```

一つでも崩れていたら、機能追加を止めて是正する。

## 付録A. 用語集

| 用語 | 定義 |
|---|---|
| **気づき（Insight）** | 観察した現象・プレイヤーの解釈・確かめた経験の三つが揃った理解の単位 |
| **観察ノート** | 本作唯一の知識UI。プレイヤーの行動によってのみ埋まる |
| **性格プロファイル** | 個体ごとの内的論理。一貫しているが、プレイヤーには直接見えない |
| **悪循環** | 過干渉によって生じる、数日単位で持続する後退状態。必ず出口がある |
| **痕跡** | 猫を直接見なくても得られる情報（食器・トイレ・毛・動いた物） |
| **決断** | 30日目にプレイヤーが行う判断。勝敗ではない |
| **不可侵条項** | 変更・例外化が一切許されない10の条項（§1.2） |
| **コア体験ループ** | 観察→仮説→行動→反応→理解→観察（§3.3）。L1レイヤー |

## 付録B. 禁止事項一覧（クイックリファレンス）

### システム
- レベル / 経験値 / 能力値成長
- 攻撃 / 戦闘 / 勝敗
- スコア / ランキング / ゲームオーバー
- ガチャ / 確率課金 / スタミナ課金
- 猫への命令 / 猫の直接操作
- 猫の育成 / 能力インフレ

### UI
- 好感度・信頼度・ストレス値などの数値表示
- 未取得コンテンツの「？？？」表示による収集誘導
- 残り日数を焦燥として強調する演出
- 3階層を超える情報階層

### 表現
- 猫への暴力・虐待の選択肢化
- 誇張されたアニメ的感情表現
- 実在の団体・業種・個人の敵役化
- 同情を煽る過去の切り売り
- 死・重篤疾病の脅威としての利用

### テキスト
- プレイヤーへの叱責・説教・断罪
- 正解の断定
- チュートリアルでの生態講義
- クイズ・正誤判定
- 禁止語彙（§10.2）の使用

### 学習
- 報酬による学習誘導
- 現象より先に知識を提示すること
- 監修を経ていない事実記述
